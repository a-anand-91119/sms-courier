**Create `UATTest.kt` marker interface** at `app/src/test/java/dev/notyouraverage/smscourier/UATTest.kt`:

```kotlin
package dev.notyouraverage.smscourier

/**
 * JUnit 4 category marker interface for UAT (User Acceptance Testing) tests.
 *
 * Annotate UAT tests with @Category(UATTest::class) to include them in the
 * grouped UAT test suite. Run all UAT tests with: ./gradlew uatTest
 */
interface UATTest
```

This is a standard JUnit 4 `@Category` marker interface. No dependencies needed -- `org.junit.experimental.categories.Category` is included in JUnit 4.13.2.

**Add `uatTest` Gradle task** to `app/build.gradle.kts`:

Register a new test task named `uatTest` that runs only tests annotated with `@Category(UATTest::class)`:

```kotlin
tasks.register<Test>("uatTest") {
    description = "Runs all UAT tests annotated with @Category(UATTest::class)"
    group = "verification"

    useJUnit {
        includeCategories("dev.notyouraverage.smscourier.UATTest")
    }

    // Use same classpath and test source sets as the default test task
    testClassesDirs = tasks.named<Test>("testDebugUnitTest").get().testClassesDirs
    classpath = tasks.named<Test>("testDebugUnitTest").get().classpath
}
```

Note: If the project uses AGP (Android Gradle Plugin) and `testDebugUnitTest` is the actual test task name, reference that. Check existing Gradle task names first with `./gradlew tasks --group verification` to get the exact test task name.

If the `tasks.register<Test>` approach doesn't work with AGP, the alternative is to add a JVM argument to the existing test task. In that case, create a simpler approach: just document in the marker interface that users run:
```bash
./gradlew test -Dtest.single="*" -Puat.only=true
```
Or more reliably, use the built-in Gradle test filtering combined with `@Category`:
```bash
./gradlew testDebugUnitTest --tests "*" -PincludeCategories=dev.notyouraverage.smscourier.UATTest
```

The simplest reliable approach is to just register the task and let the executor iterate if it needs adjustment for AGP.

**HOME-01 test (add to HomeViewModelTest.kt):**

Add a test method named `UAT HOME-01 - TARGET device with active session shows FORWARDING_TO direction not RECEIVING_FROM` (or similar with HOME-01 in the name). Annotate the test with `@Category(UATTest::class)` (import `org.junit.experimental.categories.Category` and `dev.notyouraverage.smscourier.UATTest`).

The bug: HomeScreen.kt shows `receivingFromCount` with label "Receiving" and `forwardingToCount` with label "Forwarding" — but the semantics are SWAPPED. A TARGET device (which forwards/sends messages) gets `Direction.RECEIVING_FROM` and the UI labels that "Receiving". The correct label for a TARGET device should be "Forwarding".

However, the direction-to-label mapping is currently inline in Compose (HomeScreen.kt lines ~716-727). The HOME-01 test should verify the behavior from the ViewModel perspective. The approach:

Write a test that:
1. Creates a TARGET device with `DeviceRole.TARGET` and an active session for its phone number
2. Emits the device via `approvedDevicesFlow` and session via `activeSessionsFlow`
3. Asserts on `homeState.directionalStatus`:
   - The session for the TARGET device should have direction `Direction.FORWARDING_TO` (meaning "this device forwards TO the source")

This test will FAIL because `calculateDirectionalStatus` currently maps TARGET -> `RECEIVING_FROM` (line 108-119 of HomeViewModel.kt). The fix in Phase 25 can either:
- Change the direction mapping so TARGET -> FORWARDING_TO, or
- Extract a label function and fix the labels

The test should use:
```kotlin
val targetDevice = createTestDevice(
    phoneNumber = "+5551234567",
    role = DeviceRole.TARGET,
    status = PairingStatus.APPROVED,
)
val session = createTestSession(
    id = 1L,
    devicePhoneNumber = "+5551234567",
)
```

Assert: `state.directionalStatus.activeSessions[0].direction == Direction.FORWARDING_TO`
This FAILS because current code returns `Direction.RECEIVING_FROM` for TARGET devices.

Also assert: `state.directionalStatus.forwardingToCount == 1` (FAILS: currently 0, receivingFromCount is 1 instead)
