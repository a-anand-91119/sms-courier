**Root cause analysis:**
The issue occurs in two places:

1. **SmsCommandHandler.kt:165-180** - `handleUnpair()` deletes ALL roles for a phone number:
   - Line 172: `deviceRepository.deleteByPhoneNumber(senderPhone)` removes both SOURCE and TARGET
   - Line 177: Sends UNPAIR confirmation, causing other device to also delete all roles

2. **PairedDevicesViewModel.kt:33-42** - `deleteDevice()` may not be role-specific:
   - Line 40: `deviceRepository.delete(device)` needs verification of implementation
   - Should use role-specific deletion

**Key insight:** When Device A deletes its SOURCE role to Device B:
- Device A sends UNPAIR to Device B
- Device B receives UNPAIR and deletes ALL roles for Device A (including its SOURCE to Device A)
- Device B sends UNPAIR confirmation back to Device A
- Device A receives UNPAIR and deletes its remaining TARGET role to Device B

Result: Both directions deleted when only one should be removed.

**Problem:** handleUnpair (lines 165-180) deletes ALL roles when it should only delete the role being unpaired.

**Current logic flaw:**
```kotlin
// Current: Deletes BOTH SOURCE and TARGET roles
deviceRepository.deleteByPhoneNumber(senderPhone)
```

**Fix approach:**
The UNPAIR command needs context about WHICH role is being deleted. Since the sender initiated the unpair, we need to infer which role on OUR device corresponds to their action.

**Role inference:**
- If sender has SOURCE role on their device → they're unpairing from receiving our forwards → delete our TARGET role
- If sender has TARGET role on their device → they're unpairing from sending forwards to us → delete our SOURCE role

**Implementation:**
1. Query for both roles: `deviceRepository.getByPhoneNumber(senderPhone)`
2. For each role found, determine which one to delete:
   - If they unpaired their SOURCE → delete our TARGET (we were forwarding TO them)
   - If they unpaired their TARGET → delete our SOURCE (we were requesting FROM them)
3. Since we can't know which role THEY deleted, the safest approach is:
   - **Don't send UNPAIR confirmation** (this creates the ping-pong deletion)
   - Instead: Delete the inverse role that matches the unpair direction

**Simpler fix (recommended):**
Since we can't determine which specific role was deleted on the sender's side, make handleUnpair delete only ONE role based on what exists:

```kotlin
suspend fun handleUnpair(senderPhone: String) {
    Log.i(TAG, "Unpair from: $senderPhone")

    val devices = deviceRepository.getByPhoneNumber(senderPhone)
    if (devices.isEmpty()) {
        Log.w(TAG, "Unpair from unknown device: $senderPhone")
        return
    }

    // End sessions for this phone number
    sessionRepository.endSessionForDevice(senderPhone, "UNPAIR")

    // Delete all roles for this phone (they initiated unpair, remove all connections)
    // This is correct - when they send UNPAIR, they want to disconnect completely
    deviceRepository.deleteByPhoneNumber(senderPhone)
    Log.i(TAG, "Device $senderPhone unpaired (removed ${devices.size} role(s))")

    // DO NOT send UNPAIR confirmation - this causes bidirectional deletion
    // The sender already knows they unpaired - no need to confirm
    // Removed: smsSender.sendUnpair(senderPhone)
}
```

**Critical change:** Remove the UNPAIR confirmation at line 177. This confirmation is what causes the bidirectional deletion cascade.

**Rationale:** When Device A deletes Device B, Device A sends UNPAIR to notify Device B. Device B should remove its records of Device A without sending confirmation back. Sending confirmation creates a ping-pong effect.

**Problem discovered during testing:** When Device A deletes its SOURCE role and sends UNPAIR, Device B's handleUnpair still deletes ALL roles (both SOURCE and TARGET) instead of just the corresponding role.

**Solution:** Extend UNPAIR command to include the role that should be deleted on the receiving device.

**Protocol change:**
- Current: `SMSC UNPAIR`
- New: `SMSC UNPAIR <ROLE>` where ROLE is SOURCE or TARGET

**Role logic (the inverse relationship):**
When Device A deletes its SOURCE role to Device B:
- A's SOURCE means: A requests forwarding FROM B
- On B's device: B is TARGET (B forwards TO A)
- A should send: `SMSC UNPAIR TARGET` (telling B to delete its TARGET role)

When Device A deletes its TARGET role to Device B:
- A's TARGET means: A forwards TO B (B requests FROM A)
- On B's device: B is SOURCE (B requests FROM A)
- A should send: `SMSC UNPAIR SOURCE` (telling B to delete its SOURCE role)

**Implementation steps:**

1. **Update CommandPatterns.kt:**
```kotlin
// Current:
val UNPAIR = """^SMSC\s+UNPAIR\s*$""".toRegex(RegexOption.IGNORE_CASE)

// New (make role optional for backward compatibility):
val UNPAIR = """^SMSC\s+UNPAIR(?:\s+(SOURCE|TARGET))?\s*$""".toRegex(RegexOption.IGNORE_CASE)
```

2. **Update CommandParser.kt:**
```kotlin
// Add role parameter to ParsedCommand.Unpair
data class Unpair(
    val senderPhoneNumber: String,
    val roleToDelete: DeviceRole? = null  // null for backward compatibility
) : ParsedCommand()

// Parse role from UNPAIR command:
CommandPatterns.UNPAIR.matchEntire(message)?.let { match ->
    val role = match.groupValues.getOrNull(1)?.let { roleStr ->
        when (roleStr.uppercase()) {
            "SOURCE" -> DeviceRole.SOURCE
            "TARGET" -> DeviceRole.TARGET
            else -> null
        }
    }
    return ParsedCommand.Unpair(senderPhoneNumber, role)
}
```

3. **Update SmsCommandHandler.handleUnpair:**
```kotlin
suspend fun handleUnpair(senderPhone: String, roleToDelete: DeviceRole? = null) {
    Log.i(TAG, "Unpair from: $senderPhone, role: $roleToDelete")

    if (roleToDelete != null) {
        // Role-specific deletion
        val device = deviceRepository.getByPhoneNumberAndRole(senderPhone, roleToDelete)
        if (device != null) {
            sessionRepository.endSessionForDevice(senderPhone, "UNPAIR")
            deviceRepository.deleteByPhoneNumberAndRole(senderPhone, roleToDelete)
            Log.i(TAG, "Device $senderPhone unpaired (removed $roleToDelete role)")
        } else {
            Log.w(TAG, "Unpair: $roleToDelete role not found for $senderPhone")
        }
    } else {
        // Legacy behavior: delete all roles (for backward compatibility)
        val devices = deviceRepository.getByPhoneNumber(senderPhone)
        if (devices.isNotEmpty()) {
            sessionRepository.endSessionForDevice(senderPhone, "UNPAIR")
            deviceRepository.deleteByPhoneNumber(senderPhone)
            Log.i(TAG, "Device $senderPhone unpaired (removed ${devices.size} role(s) - legacy)")
        }
    }

    // Still no confirmation - fixed in Task 1
}
```

5. **Update PairedDevicesViewModel.deleteDevice:**
```kotlin
fun deleteDevice(device: PairedDevice) {
    viewModelScope.launch {
        sessionRepository.endSessionForDevice(device.phoneNumber, "USER")

        // Send role-specific UNPAIR - tell other device to delete the inverse role
        val roleToDeleteOnRemote = when (device.role) {
            DeviceRole.SOURCE -> DeviceRole.TARGET  // We're SOURCE, they're TARGET
            DeviceRole.TARGET -> DeviceRole.SOURCE  // We're TARGET, they're SOURCE
        }
        smsSender.sendUnpair(device.phoneNumber, roleToDeleteOnRemote)

        // Delete only this specific role from local database
        deviceRepository.deleteByPhoneNumberAndRole(device.phoneNumber, device.role)
    }
}
```

```kotlin
is ParsedCommand.Unpair -> handleUnpair(command.senderPhoneNumber, command.roleToDelete)
```

- New clients sending `SMSC UNPAIR SOURCE|TARGET` will do role-specific deletion
- This allows gradual rollout without breaking existing installations
