**Root cause analysis:**
The issue occurs in two places:

1. **SmsCommandHandler.kt:165-180** - `handleUnpair()` deletes ALL roles for a phone number:
   - Line 172: `deviceRepository.deleteByPhoneNumber(senderPhone)` removes both SOURCE and TARGET
   - Line 177: Sends UNPAIR confirmation, causing other device to also delete all roles

2. **PairedDevicesViewModel.kt:33-42** - `deleteDevice()` may not be role-specific:
   - Line 40: `deviceRepository.delete(device)` needs verification of implementation
   - Should use role-specific deletion

**Key insight:** When Device A deletes its SOURCE role to Device B:
- Device A sends UNPAIR to Device B
- Device B receives UNPAIR and deletes ALL roles for Device A (including its SOURCE to Device A)
- Device B sends UNPAIR confirmation back to Device A
- Device A receives UNPAIR and deletes its remaining TARGET role to Device B

Result: Both directions deleted when only one should be removed.
</context>

**Problem:** handleUnpair (lines 165-180) deletes ALL roles when it should only delete the role being unpaired.

**Current logic flaw:**
```kotlin
// Current: Deletes BOTH SOURCE and TARGET roles
deviceRepository.deleteByPhoneNumber(senderPhone)
```

**Fix approach:**
The UNPAIR command needs context about WHICH role is being deleted. Since the sender initiated the unpair, we need to infer which role on OUR device corresponds to their action.

**Role inference:**
- If sender has SOURCE role on their device → they're unpairing from receiving our forwards → delete our TARGET role
- If sender has TARGET role on their device → they're unpairing from sending forwards to us → delete our SOURCE role

**Implementation:**
1. Query for both roles: `deviceRepository.getByPhoneNumber(senderPhone)`
2. For each role found, determine which one to delete:
   - If they unpaired their SOURCE → delete our TARGET (we were forwarding TO them)
   - If they unpaired their TARGET → delete our SOURCE (we were requesting FROM them)
3. Since we can't know which role THEY deleted, the safest approach is:
   - **Don't send UNPAIR confirmation** (this creates the ping-pong deletion)
   - Instead: Delete the inverse role that matches the unpair direction

**Simpler fix (recommended):**
Since we can't determine which specific role was deleted on the sender's side, make handleUnpair delete only ONE role based on what exists:

```kotlin
suspend fun handleUnpair(senderPhone: String) {
    Log.i(TAG, "Unpair from: $senderPhone")

    val devices = deviceRepository.getByPhoneNumber(senderPhone)
    if (devices.isEmpty()) {
        Log.w(TAG, "Unpair from unknown device: $senderPhone")
        return
    }

    // End sessions for this phone number
    sessionRepository.endSessionForDevice(senderPhone, "UNPAIR")

    // Delete all roles for this phone (they initiated unpair, remove all connections)
    // This is correct - when they send UNPAIR, they want to disconnect completely
    deviceRepository.deleteByPhoneNumber(senderPhone)
    Log.i(TAG, "Device $senderPhone unpaired (removed ${devices.size} role(s))")

    // DO NOT send UNPAIR confirmation - this causes bidirectional deletion
    // The sender already knows they unpaired - no need to confirm
    // Removed: smsSender.sendUnpair(senderPhone)
}
```

**Critical change:** Remove the UNPAIR confirmation at line 177. This confirmation is what causes the bidirectional deletion cascade.

**Rationale:** When Device A deletes Device B, Device A sends UNPAIR to notify Device B. Device B should remove its records of Device A without sending confirmation back. Sending confirmation creates a ping-pong effect.
