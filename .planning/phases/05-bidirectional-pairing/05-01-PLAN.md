# Plan 05-01: Bidirectional Pairing Architecture

**Phase**: 5 - Bidirectional Pairing Architecture
**Goal**: Enable same phone number to exist in both "Forwarded to me" and "I forward to" sections simultaneously
**Status**: Not Started

## Context

Currently, the `phoneNumber` field is used as the sole PRIMARY KEY in the `PairedDevice` entity, enforcing a database-level constraint that only one row per phone number can exist. This prevents the same phone number from being paired in both SOURCE and TARGET roles.

**Research findings** (from explore agent):
- Primary constraint: `PairedDevice.kt` line 32 - `@PrimaryKey val phoneNumber: String`
- Business logic checks in `SmsCommandHandler.kt` (lines 345-349, 78-112) reject existing phone numbers
- `AddDeviceViewModel.kt` (lines 42-50) validates against any existing device
- DAO uses `OnConflictStrategy.REPLACE` which would overwrite the role

**Goal**: Update pairing logic to handle bidirectional scenarios

#### 3.1 Update SmsCommandHandler

**Update initiatePairing** (lines 345-349):

**Current**:

**Change to**:
```kotlin
suspend fun initiatePairing(targetPhoneNumber: String) {
    // Check if SOURCE role already exists for this phone number
    val existingSource = deviceRepository.getByPhoneNumberAndRole(
        targetPhoneNumber,
        DeviceRole.SOURCE
    )

    if (existingSource != null) {
        Log.w(TAG, "SOURCE pairing already exists for $targetPhoneNumber with status ${existingSource.status}")
        return
    }

    // It's OK if TARGET role exists - bidirectional pairing is allowed
    val existingTarget = deviceRepository.getByPhoneNumberAndRole(
        targetPhoneNumber,
        DeviceRole.TARGET
    )
    if (existingTarget != null) {
        Log.d(TAG, "TARGET pairing exists for $targetPhoneNumber - creating bidirectional pair")
    }
```

**Update handlePairRequest** (lines 78-112):

**Current**:
```kotlin
suspend fun handlePairRequest(senderPhone: String) {
    val existing = deviceRepository.getByPhoneNumber(senderPhone)
    when (existing?.status) {
        PairingStatus.APPROVED -> {
            Log.d(TAG, "Already approved device: $senderPhone")
            return
        }
```

**Change to**:
```kotlin
suspend fun handlePairRequest(senderPhone: String) {
    // Check if TARGET role already exists (this device forwards TO sender)
    val existingTarget = deviceRepository.getByPhoneNumberAndRole(
        senderPhone,
        DeviceRole.TARGET
    )

    when (existingTarget?.status) {
        PairingStatus.APPROVED -> {
            Log.d(TAG, "Already approved as TARGET: $senderPhone - ignoring duplicate")
            return
        }
        PairingStatus.PENDING_APPROVAL -> {
            Log.d(TAG, "Pending approval as TARGET: $senderPhone - ignoring duplicate")
            return
        }
        null -> {
            // No existing TARGET pairing
            // Check if SOURCE role exists (bidirectional)
            val existingSource = deviceRepository.getByPhoneNumberAndRole(
                senderPhone,
                DeviceRole.SOURCE
            )
            if (existingSource != null) {
                Log.d(TAG, "SOURCE pairing exists - creating bidirectional pair")
            }
        }
    }
```

### Task 4: Edge Case Testing

**Goal**: Test bidirectional pairing scenarios

#### Test Cases:

1. **Sequential pairing**:
   - Device A pairs with Device B (A=SOURCE, B=TARGET)
   - Device B then pairs with Device A (B=SOURCE, A=TARGET)
   - Result: Both bidirectional pairs exist

2. **Simultaneous pairing**:
   - Device A sends PAIR_REQUEST to Device B
   - Device B sends PAIR_REQUEST to Device A (before approving A's request)
   - Both devices approve
   - Result: Both bidirectional pairs exist

3. **Duplicate requests**:
   - Device A already paired as SOURCE to Device B
   - Device A tries to pair as SOURCE to Device B again
   - Result: Request rejected (duplicate SOURCE)

4. **Delete one direction**:
   - Both directions exist
   - Delete SOURCE role
   - Result: TARGET role persists

5. **Status conflicts**:
   - Device A paired as SOURCE with PENDING status
   - Device B tries to pair as TARGET
   - Result: Should allow or handle gracefully
